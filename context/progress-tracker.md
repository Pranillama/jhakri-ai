- Canvas autosave conflict fix: fixed the two data-loss races flagged by the pre-deploy code-review pass (see the round-1 entry below) and deliberately deferred pending a design decision — discussed with the user, who chose "make the server the source of truth" over accepting the risk or building full optimistic-concurrency version checks (the latter judged more engineering than this stage warrants for a race this narrow; noted as the textbook-correct option if it's ever actually hit at scale). **Race A — a stale Blob load overwriting live work.** `canvas.tsx`'s `loadSavedCanvas` checked `nodes.length > 0 || edges.length > 0` once, then awaited a fetch, then applied the result unconditionally — if Storage went from empty to non-empty *during* the fetch (an AI run starting, or another tab's own load landing first), the old Blob snapshot would clobber it. Fixed with the same "ref mirrors live state every render" pattern `useCanvasAutosave` already uses for its own staleness problem: a new `liveGraphRef` is kept in sync via its own `useEffect`, and `loadSavedCanvas` re-checks `liveGraphRef.current` right before calling `setNodes`/`setEdges` — if Storage is no longer empty by then, the fetched snapshot is silently discarded instead of applied. Also let `nodes`/`edges` drop out of the load effect's dependency array, since the effect only reads them through the ref now. **Race B — concurrent autosaves overwriting the Blob snapshot.** `PUT /api/projects/[projectId]/canvas` used to trust whatever graph the client's request body carried, built from `useCanvasAutosave`'s `graphRef` (that client's local, possibly-lagging copy of Storage — network jitter or a backgrounded tab could mean it's stale right when the debounced save fires). Since every save is a full blind overwrite (`allowOverwrite: true`, no version check), a stale client-supplied snapshot could silently regress what a later reload or cold-open sees, even though the live room itself stayed correct throughout for anyone connected. Fixed by making the route ignore the client body entirely and instead call `readCanvasSnapshot(projectId)` — the same Liveblocks Storage reader `lib/design-canvas.ts`'s design agent already uses — so every save persists the one converged source of truth directly, not a client's copy of it; `roomId`/`projectId` are the same identifier in this app (see Architecture Decisions), so no extra lookup was needed. `useCanvasAutosave`'s `save()` now sends a bodyless `PUT`; its `nodes`/`edges` params still exist purely as the change-detection signal that schedules the debounced save, documented as such. This narrows Race B's remaining exposure to ordinary write-ordering on the same source of truth (never a regression) rather than eliminating all timing windows outright — which is exactly what "make Storage the source of truth" was chosen over full versioning to accept. - 23-design-agent-logic: the design agent turns a prompt into real-time canvas updates with visible AI presence and status (`npm run build` + `tsc --noEmit` + `eslint` pass; **verified end to end** against the live Trigger.dev cloud, Liveblocks, and Gemini — see the verification note at the end of this entry). `trigger/design-agent.ts` is now a `schemaTask` (zod payload `{ prompt, roomId }`, re-validated at the task boundary on top of the route's check) that orchestrates four small modules and publishes progress throughout. **`lib/design-model.ts`** calls Gemini via `@ai-sdk/google` + `generateObject`; the system prompt carries the operating rules (shape meanings derived from `NODE_SHAPES`, the palette names, tier-coloring conventions, left-to-right layout direction, one-node-per-cell, connect-what-you-add, and a "do only what was asked" scope rule). **`lib/design-actions.ts`** owns the response schema, the validated `DesignAction` union, and `flattenDesignPlan`. **`lib/design-layout.ts`** owns the placement grid. **`lib/design-canvas.ts`** reads and writes the graph. **`lib/ai-activity.ts`** (`AiActivityPublisher`) publishes presence + status. Key design decisions, each of them load-bearing: (1) **The model never picks a number.** It names a shape, a palette color, a grid cell, and a size; pixels, hex values, and positions are computed from those names in code. That is what makes "generated designs follow the allowed shapes, color palette, and layout/spacing rules" a guarantee rather than a request — `positionForCell` centers each node in a 320×240 cell (wider/taller than the largest node, so a minimum 130px horizontal and 100px vertical gap is arithmetic, not luck), and a `CellAllocator` in `flattenDesignPlan` pushes a node down a row if the model asks for an occupied cell, so overlap is impossible even when the model repeats itself. It also turned out to be a hard robustness requirement, not just tidiness — see the schema note below. (2) **Canvas writes go through `mutateFlow` from `@liveblocks/react-flow/node`**, the server-side half of the same package `useLiveblocksFlow` uses on the client, so the agent writes the canvas through the existing collaborative flow rather than hand-rolling Storage mutations; `readCanvasSnapshot` uses the same call with a no-op callback so reads and writes share one API. (3) **Each action is applied in its own `mutateFlow` call**, not batched — the diagram builds up node by node in front of everyone in the room with the agent's cursor moving ahead of each change, which is the point of running this on a collaborative canvas. (4) **AI presence uses `Liveblocks.setPresence`** (the ephemeral REST presence API, TTL refreshed on every status update), so the agent is a real participant and `LiveCursors` / `PresenceAvatars` render it with **no special-casing** — the only client change needed was a pulsing dot on the cursor badge when `presence.thinking` is set. Presence is cleared in a `finally` with a 2s TTL so the agent leaves the room whatever happened. (5) **Superseded by 24-ai-presence-state — the status feed is now a Liveblocks feed (`ai-status-feed`) and the Storage `ai` key no longer exists.** As originally built: **the status feed lives in Storage, not broadcast events** — a durable `ai` key (`AI_STATUS_KEY`) holding `{ runId, state, message, updatedAt, activity[] }`, so all participants see the same messages and someone joining mid-run sees them too; broadcasts would be invisible to a late joiner. `liveblocks.config.ts` types Storage as `{ ai?: AiCanvasStatus }` (optional, so `RoomProvider` still needs no `initialStorage`; the `flow` subtree stays owned/typed by the package).   - **Response schema shape — the hard-won part.** The plan schema is one array per kind of change (`addNodes`, `updateNodes`, `moveNodes`, `resizeNodes`, `deleteNodes`, `addEdges`, `deleteEdges`) rather than a single list of mixed action objects. That is the third design tried, and the first two failed against real Gemini calls in ways worth recording. A **discriminated union** (`z.discriminatedUnion("action", …)`) is the natural model, but Gemini's structured output resolves `anyOf` loosely and invents its own property names inside it — asked for `column`/`label`/`shape` it returned `col`/`text`/`type`/`metadata`. A **single flat object with optional fields** keeps the property names, but Gemini fills in *every* declared property regardless of relevance, so on an "add node" it had to invent an edge `target` — and what it invented was a degenerate, ever-growing string that consumed the entire output budget and failed the run (one observed run burned 65k output tokens emitting a single 60,000-digit `width`; another used the `target` field as scratch space for its own chain of thought). Grouping by change type gives every object only the fields it needs, so nothing has to be invented. This is also why `resize_node` takes a size *name* (`small`/`medium`/`large`, resolved against the shape's default dimensions) instead of pixel width/height, and why grid cells are clamped to ±200 — no open-ended numeric or free-text field is left for the model to wander off in. Execution order is fixed by `flattenDesignPlan` (removals → new nodes → node edits → moves → resizes → edges) rather than chosen by the model, which is strictly better than trusting the ordering of a flat list. All seven actions the spec requires are still supported; only how they are requested changed.

## Architecture Decisions

- Liveblocks auth uses access tokens (`prepareSession`), not ID tokens. The route already performs the authoritative access check via `getAccessibleProject`, so it grants `FULL_ACCESS` to the verified room directly in the session token rather than relying on per-user room permissions. The room is still created up front (`getOrCreateRoom` with `defaultAccesses: []`, private) so it exists before connection and can later carry metadata; with access tokens the private default doesn't block the granted session. The spec's "return a session token" wording matches this model.
- Project ID == Liveblocks room ID. The create flow generates `<slug>-<suffix>` client-side and sends it as the project `id`; `POST /api/projects` persists it (validated, URL-safe) instead of always using the cuid default, so the DB record and the future room share one identifier. This extends 06's "use the schema's ID strategy" — cuid remains the fallback when no valid id is supplied. `POST` returns 409 on a `P2002` id collision (duplicated/retried create).
- Workspace route param is `[roomId]`, per spec 08. Because project ID == Liveblocks room ID, the dynamic segment value is the project ID; the create flow's `router.push(/editor/${project.id})` lands on it directly. Access is gated by a single `findFirst` (owner OR collaborator-by-email) in `lib/project-access.ts` — both "project missing" and "no access" collapse to `AccessDenied`, so the route never reveals which projects exist to unauthorized users.
- Collaborator emails are stored lowercased (normalized in `parseCollaboratorEmail` on invite) and membership is matched against the signed-in user's full set of **verified** emails (lowercased; primary always included), not just the primary — so an invite to a secondary address still grants access. Unverified emails are excluded so an unverified address can't be used to claim an invite. No local user table — Clerk is the source of truth for profile data, fetched on demand via the Backend API and never persisted (per spec 09). Clerk enrichment is best-effort: a failed lookup falls back to email-only rather than failing the request.
- Canvas state lives in Liveblocks Storage, not the DB. `useLiveblocksFlow` (suspense) is the single source of truth for nodes/edges in-session; the page stays a server component for access control while the canvas subtree is client-only (`LiveblocksProvider`/`RoomProvider` under `editor-room-shell`). The room is the project ID, so the `authEndpoint` reuses the same `getAccessibleProject` gate. Suspense + `ClientSideSuspense` keeps the static workspace chrome rendered while only the canvas waits on the realtime connection; a class-based error boundary isolates connection failures to the canvas instead of taking down the shell. Persisting the graph to Vercel Blob (`canvasJsonPath`) was deferred to a later unit per the workflow's "don't combine realtime canvas state and DB persistence" split rule — done in 21-canvas-autosave, which layers a durable snapshot on top without changing this in-session source of truth.
- Starter template import replaces the canvas through React Flow's controlled-flow diff, not a bespoke clear path. `reactFlow.setNodes(next)`/`setEdges(next)` in this no-`defaultNodes` setup run xyflow's `getElementsDiffChanges` (verified in `@xyflow/react`), which emits `remove` changes for every current element absent from `next` plus `add`/`replace` for the new ones, and dispatches them through the same `onNodesChange`/`onEdgesChange` the Liveblocks integration owns. So passing the template's nodes/edges wholesale clears the old graph and adds the new one in one collaborative, synced operation — no separate "delete all" call, and no risk of stacking on top. Templates are deep-`structuredClone`d at import time because they are shared module constants and React Flow mutates node internals in place. The modal lives inside `<Canvas>` (not the shell) so the import handler has React Flow + Liveblocks context for `setNodes`/`setEdges`/`fitView`; only its open/close boolean is lifted to `editor-room-shell` and threaded down so the navbar (outside the room) can trigger it.

- Ownership enforcement is atomic with the write (code-review fix). `PATCH`/`DELETE` no longer pre-check ownership in a separate query (TOCTOU window); they scope the mutation to `where: { id, ownerId }` and catch Prisma `P2025`. On that not-found path, `resolveMutationFailureStatus` in `lib/projects.ts` does a single existence read to pick 403 (exists, other owner) vs 404 (missing). The old `checkProjectOwnership`/`ProjectOwnershipResult` were removed.
- Canvas snapshots are saved as **private** Vercel Blobs, not public ones. The blob path is deterministic (`canvas/{projectId}.json`), so a public blob would be a guessable URL exposing a project's architecture diagram to anyone who has it, with no auth check. Private access means the save/load routes are the only path to the content — both already gate on `getAccessibleProject` — at the cost of reading via the SDK's `get()` (server-side, token-authenticated) instead of a bare `fetch(url)`. Save/load are open to any project member (owner or collaborator), unlike the owner-only collaborator-management mutations, because the canvas itself is already collaboratively editable by anyone with room access — restricting the save endpoint further would just mean collaborators' edits silently stop persisting.
- Shared AI status is one Liveblocks feed, `ai-status-feed`, and nothing else. Feeds are a first-class feature of the installed SDK, so the app uses them rather than reimplementing a feed on top of Storage (which is what Phase 24 originally did) or on broadcast events (invisible to a late joiner). The payload is validated on both the write and the read side against one zod schema in `types/tasks.ts`, and it carries a `task` discriminator so spec generation shares the channel instead of opening a second one. Exactly one hook (`useAiStatus`) reads it, exposing only the latest valid message, so no two surfaces can disagree about what the AI is doing. The Liveblocks room is therefore entered by `EditorRoomShell` rather than by the canvas — the AI sidebar is a participant in it too.
- The AI design agent is a room participant, not a special UI mode. It publishes ephemeral Liveblocks presence (`setPresence`) under its own user ID, so the cursor and avatar components render it with no AI-specific branching, and its shared progress goes to the room's status feed rather than to broadcast events so a late joiner sees the same messages. The alternative — connecting `@liveblocks/client` from the background task to get a genuine WebSocket session — was rejected: the REST presence API plus `mutateFlow` covers everything needed without a connection lifecycle to manage inside a durable task, and `@liveblocks/react-flow/node` exists precisely so backends don't need a client.
- Everything the design model chooses is a name from a closed set (shape, palette color, grid cell, size), never a raw number, hex value, or pixel coordinate. This started as a way to make the documented design rules enforceable in code, and turned out to be a hard robustness requirement: given an open-ended numeric or free-text field with no anchor, Gemini reliably degenerates into an ever-growing value that exhausts the output budget. The response schema is grouped one array per change type for the same reason — see the 23-design-agent-logic entry for the two schema shapes that failed and why.
- A design run is started by one participant but watched by everyone, on two different channels. The `ai-status-feed` is the shared channel: it drives the canvas banner and locks every participant's composer, so a run someone else started is visible and non-collidable for the whole room. The Trigger.dev run subscription (`useRealtimeRun` + a run-scoped public token) is the private one: only the participant who started the run holds a token, so only they subscribe, and only they post the closing summary into `ai-chat` — which is exactly what keeps that summary from being published once per connected client. The two are OR'd for "is a run active" because neither covers the whole window: the feed is silent before the task's first publish, and the subscription doesn't exist for anyone else in the room.
- Canvas-load fetch failures are caught, not left to reject (code-review fix). `components/editor/canvas/canvas.tsx`'s one-time `loadSavedCanvas` effect now wraps its `fetch` in `try`/`catch` (logging via `console.error`) so a network failure during the initial load rejects gracefully instead of surfacing as an unhandled promise rejection; the existing `finally` still flips `readyForAutosave` to `true` either way, so autosave still enables even when the load fails.
- A failed `TaskRun` write now cancels its Trigger.dev run instead of leaving it orphaned (code-review fix). `app/api/ai/design/route.ts`'s `POST` used to trigger the design task and persist the `TaskRun` record in the same try/catch, so a Prisma failure after a successful trigger left a run with no ownership record — one the token route could never verify against and one that would still execute and mutate the room's canvas with nothing tying it back to a project or user. The `prisma.taskRun.create` call is now its own try/catch that calls `runs.cancel(handle.id)` (best-effort, its own rejection swallowed) before rethrowing on failure, so a persistence failure also stops the run.
- Spec generation reads the canvas and chat history from the client's request, not from Liveblocks. Unlike the design agent (which re-reads the room via `readCanvasSnapshot` so it always mutates against the freshest graph), `generate-spec` has nothing to mutate — it only produces Markdown from whatever graph and chat history it's given — so there's no correctness reason to make it re-fetch, and the feature spec asks for the client-supplied fields explicitly. `lib/spec-request.ts`'s `specCanvasPayloadSchema` is the one Zod schema both `POST /api/ai/spec` and the task validate the same client-supplied shape against, extended with a server-derived `projectId` for the task only.
- The design agent's max node size is derived from the placement grid, not a flat constant (code-review fix). `lib/design-actions.ts`'s `MAX_NODE_SIZE` used to clamp to 400×400px regardless of `lib/design-layout.ts`'s `DESIGN_GRID` cell dimensions (320×240), so a `large`-scaled diamond (180×180 default × 1.5) could exceed its cell's row height and overlap the row below — breaking the 23-design-agent-logic invariant that a node never exceeds the cell built to contain it. `MAX_NODE_SIZE` is now `{ width: Math.min(400, DESIGN_GRID.columnWidth - GRID_CLEARANCE), height: Math.min(400, DESIGN_GRID.rowHeight - GRID_CLEARANCE) }` (40px clearance), so the hard bound can never exceed what a cell can actually hold.
- A generated spec's blob path is keyed by a server-generated `specId`, minted before either write. `trigger/generate-spec.ts` builds `specId` with `crypto.randomUUID()` up front so both the Blob upload (`specs/{projectId}/{specId}.md`) and the single `ProjectSpec.create` can use the same id without a create-then-update two-step — unlike `canvasJsonPath`, which needs no such id because its blob path is deterministic per project. The download route (`specs/[specId]/download`) then scopes its lookup to `{ id: specId, projectId }` together, not `specId` alone, so a spec can never be fetched through a different project's URL even if the caller has access to both.

- Liveblocks 409-detection uses a `status` property check (`isLiveblocksStatus` in `lib/liveblocks.ts`), not `error instanceof LiveblocksError`. `getLiveblocks()` caches its client on `globalThis` to survive dev Fast Refresh, but that means a long-lived client can throw a `LiveblocksError` whose class reference is from a module instance since hot-reloaded, making `instanceof` against a freshly imported `LiveblocksError` unreliable in dev — confirmed live when a genuine 409 from `createFeed` fell through an `instanceof` check and surfaced as an unhandled 500. `ensureFeed` and `AiActivityPublisher`'s feed-creation both now use the shared helper instead of their own `instanceof` checks.
- The AI Architect composer's activity lock filters the shared status feed by `task`, not just run state (code-review fix). Once spec generation (Phase 31) started publishing `task: "spec"` messages onto the same `ai-status-feed` the design agent uses, `ArchitectTab`'s `feedActive` — previously any active-state message regardless of `task` — cross-locked the design composer while a spec run was in progress. `components/editor/ai-sidebar.tsx`'s `ArchitectTab` now requires `status.task === "design"`, matching the `status.task === "spec"` filter `SpecsTab` already had, so the two run types lock only their own tab's controls.
